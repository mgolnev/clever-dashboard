# 0008. Компактная read-модель вкладки «Цель»

- Статус: Принято
- Дата: 2026-09-13

## Контекст

Вкладка «Цель» загружала годовой план, границы данных, статус аналитики, четыре
полных отчёта `/api/metrics` и два `/api/acquisition`. Полные отчёты считают
период сравнения, товарные и клиентские срезы и дневные ряды, хотя экрану нужны
только NET, выручка, AOV, трафик и CR по трём каналам. На SQLite одна загрузка
порождала около 156 SQL-запросов и занимала на проде около 1,9 секунды.

## Решение

1. Выделить атомарный сервис `services/goal`, который формирует read-модель
   только для вкладки «Цель» и самостоятельно читает общую БД.
2. Сервис не импортирует `metrics`, `acquisition`, `plan` или `trafficsync`.
   Совпадающие правила NET/G2N закреплены SQL-предикатами нейтрального пакета
   `orderstage`, а конфигурация источников передаётся через собственный DTO.
3. Добавить обратно совместимый `GET /api/goal?year=YYYY&month=M`. Существующие
   аналитические endpoint-ы и сохранение плана через `PUT /api/plan` не менять.
4. Возвращать одним ответом годовой план, границы заказов, итоги текущего месяца,
   30-дневную историческую базу и статус источников. Для каждого периода отдавать
   только `revenue`, `netRevenue`, `aov`, `sessions` и `netCr` по `all/site/app`.
5. Frontend отменяет устаревший запрос при быстрой смене месяца или года.

## Последствия

- Загрузка «Цели» выполняет 8 компактных SQL-запросов вместо множества полных
  отчётов и требует один HTTP round trip.
- Общие `/api/metrics` и `/api/acquisition` остаются полными и не усложняются
  флагами частичного ответа.
- Формулы вкладки остаются на frontend; endpoint предоставляет минимальные
  проверяемые исходные агрегаты.
- При добавлении нового показателя в «Цель» его нужно явно включить в read-модель,
  а не подключать полный отчёт соседнего домена.
