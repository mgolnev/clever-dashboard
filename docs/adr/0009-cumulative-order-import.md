# 0009. Накопительный импорт заказов

- Статус: Принято
- Дата: 2026-09-13

## Контекст

Полная замена `orders` при каждом импорте не позволяет один раз загрузить
историю, а затем дозагружать только новые или изменённые заказы. Файл за короткий
период удалял из витрины все заказы, которых в нём не было. При этом номер заказа
стабилен, а выгрузка содержит дату последнего изменения и конечное состояние.

## Решение

1. Сделать накопительный merge единственным штатным режимом файлового импорта.
   Отсутствующие в новом файле заказы не изменяются и не удаляются.
2. Новый `order_number` вставляется. Совпавший заказ обновляется, если входящая
   `updated_at` не старше сохранённой; при отсутствии даты изменения входящий
   снимок считается авторитетным. Более старая версия пропускается.
3. Позиции каждого вставленного или обновлённого заказа заменяются целиком,
   поскольку выгрузка не предоставляет стабильный ключ строки позиции.
4. Разбор файла, merge заказов, замена их позиций и запись аудита выполняются в
   одной транзакции. Ошибка оставляет основную витрину и журнал без изменений.
5. В `raw_import` хранить счётчики добавленных, обновлённых и пропущенных заказов.
   В API оставить `ordersCleared: 0` для обратной совместимости.

## Последствия

- Историю можно загружать несколькими пересекающимися файлами и в любом порядке:
  более старый снимок не откатит свежий конечный статус.
- Повторный импорт актуального файла идемпотентен по состоянию БД; позиции не
  дублируются.
- Обычный импорт больше не является способом очистки БД. Если полная очистка
  понадобится, для неё потребуется отдельная административная операция с
  резервной копией и явным подтверждением.
- История переходов статуса не хранится: `orders` содержит только самый свежий
  принятый снимок, что соответствует аналитике по конечным статусам.
