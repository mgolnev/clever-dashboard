# 0005. Сохранение дневного трафика Метрики и AppMetrica

- Статус: Принято
- Дата: 2026-08-22

## Контекст

Дашборду нужен автоматический верх воронки для произвольных периодов: визиты
сайта, сессии приложения и конверсия в заказы Битрикса. Запрашивать Яндекс при
каждом открытии страницы нельзя: UI становится зависим от доступности внешнего
API, расходует квоту и не гарантирует воспроизводимость исторического отчёта.
Помесячная таблица `traffic` не подходит для недель и произвольных дат.

## Решение

1. Сохранять в `analytics_traffic_daily` обезличенные агрегаты
   `день × канал × источник`: сессии, пользователи (если метрика доступна),
   признаки семплирования и время синхронизации. Сырые события и пользовательские
   идентификаторы не загружать.
2. Коннекторы `connectors/metrika` и `connectors/appmetrica` реализуют один
   нейтральный контракт `trafficsync.Source`; токены существуют только в env
   backend.
3. `services/trafficsync` отвечает за backfill, повторную загрузку последних
   дней, upsert и журнал `analytics_sync_runs`. В одноконтейнерном деплое
   планировщик запускается внутри backend. Отсутствие ключей не мешает приложению.
4. `services/acquisition` независимо читает трафик и заказы из общей БД и отдаёт
   верхнюю воронку. Он не вызывает `metrics` или `traffic`.
5. Основной показатель — сессионный CR: созданные заказы / визиты сайта или
   сессии приложения. Дополнительно считаются CR в оплату и CR действующих
   (неотменённых) заказов.
6. Автоматические дневные данные агрегируются в существующий помесячный контракт
   `/api/traffic` и имеют приоритет над ручным вводом. Ручной источник остаётся
   fallback.
7. Сессии AppMetrica запрашиваются параметрами, которые экспортирует стандартный
   отчёт «Вовлечённость»: дневная группировка, `accuracy=medium` и
   `include_undefined=true`. Канонический источник для автоматизации — публичный
   Reporting API. Внутренний отчёт нового UI может незначительно отличаться даже
   при одинаковом экспортном запросе; приватный GraphQL кабинета не используется.
8. Коннектор может объявить ревизию семантики запроса. При её изменении
   `trafficsync` один раз выполняет полный backfill и сохраняет применённую
   ревизию в `analytics_source_revisions`; следующие запуски снова используют
   обычный lookback.

## Последствия

- Исторические отчёты строятся локально и не обращаются к Яндексу.
- Повторная загрузка lookback-периода учитывает поздние уточнения данных.
- Изменение определения внешней метрики автоматически пересчитывает всю
  настроенную глубину истории без ручной очистки таблиц.
- SQLite остаётся достаточным: объём — несколько строк в день, а не поток событий.
- Уникальные пользователи разных дней и каналов неаддитивны, поэтому суммарный CR
  считается по визитам/сессиям. Для сквозной идентификации людей потребовались бы
  raw logs и отдельное решение по персональным данным.
- Числитель CR свежий только настолько, насколько свежи заказы Битрикса. До
  подключения Bitrix API импорт заказов остаётся ручным.
