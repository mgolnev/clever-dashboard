# Архитектура

## Принципы

- **Атомарные независимые сервисы** (см. AGENTS.md): один модуль — одна
  ответственность; домены не импортируют внутренности друг друга.
- **Коннекторное ядро**: источники данных (файл Битрикса, в будущем Bitrix API,
  Метрика, Аппметрика) подключаются как сменные входы, не затрагивая витрину.
- **Переносимость БД**: один код работает на SQLite и Postgres (`db.IsPostgres()`).

## Поток данных

```
Файл XLS/CSV ──► importupload (части) ──► ingestion (поток) ──► normalize
                                                                    │
                                                                    ▼
                                             orders (raw_import, orders, order_items)
                                                  │
                                                  ▼
                                              metrics ──► HTTP API ──► React-дашборд

Метрика / AppMetrica ──► connectors ──► trafficsync ──► analytics_traffic_daily
                     └──► ecomsync ─────► analytics_ecommerce_daily
                                                │
orders ─────────────────────────────────────────┴───────────────► acquisition ──► HTTP API
orders + traffic + plan ────────────────────────────────────────► goal ─────────► HTTP API
```

## Модули (Go)

| Пакет | Ответственность | Зависит от |
|-------|-----------------|------------|
| `ingestion` | Парсинг файла Битрикса (HTML/CSV), разбор позиций | `normalize`, `model` |
| `services/importupload` | Временные сессии и сборка частей больших файлов | файловая система |
| `normalize` | Деньги, гео, статусы→стадии, атрибуты товара | — |
| `services/orders` | Импорт, дедуп, хранение витрины | `ingestion`, `model`, `db` |
| `services/metrics` | KPI, воронка, срезы, сравнение периодов | `db` |
| `connectors/metrika`, `connectors/appmetrica` | Чтение дневных агрегатов Reporting API | `model` |
| `services/trafficsync` | Backfill, upsert и журнал синхронизации | `db`, контракт источника |
| `services/ecomsync` | Backfill дневной аудитории E-commerce этапов | `db`, контракт источника |
| `services/acquisition` | Трафик, E-commerce воронка и CR по каналам | `db` |
| `services/goal` | Компактная read-модель плана, NET и трафика для вкладки «Цель» | `db`, `orderstage` |
| `handlers` | HTTP (Fiber), валидация входа | `container` |
| `container` | DI: сборка зависимостей | все сервисы |

`orders` и `metrics` не вызывают друг друга — связь только через общую БД и
нейтральный пакет `model`.

`goal` также не вызывает `metrics`, `acquisition`, `plan` или `trafficsync`:
это самостоятельная оптимизированная read-модель поверх общей БД. Решение и
границы контракта описаны в [ADR-0008](adr/0008-compact-goal-read-model.md).

Импорт читает файл построчно и передаёт в `orders` батчи по 200 заказов. Все
батчи входят в одну транзакцию накопительного merge, поэтому частично
загруженные данные не становятся видимыми. Новые номера добавляются, совпавшие
обновляются более свежим снимком, отсутствующие в файле заказы сохраняются
([ADR-0009](adr/0009-cumulative-order-import.md)).

## Модель данных

- **`raw_import`** — журнал загрузок (файл, период, счётчики). История и аудит.
- **`orders`** — нормализованный заказ (PK = `order_number`, дедуп при повторной загрузке).
- **`order_items`** — позиции заказа (из столбца «Позиции») с атрибутами товара.
- **`analytics_traffic_daily`** — обезличенные дневные визиты/сессии и пользователи по каналу.
- **`analytics_ecommerce_daily`** — обезличенная дневная аудитория событий просмотра, корзины, checkout и purchase.
- **`analytics_sync_runs`** — аудит попыток загрузки внешней аналитики.

Время хранится строкой `YYYY-MM-DD HH:MM:SS` — лексикографически сравнимо в
SQLite и корректно приводится в Postgres; фильтры периода работают одинаково.

## Расчёт периодов

Длина периода `L = end − start + 1` дней. Предыдущий период —
`[start − L, start − 1]` (та же длина, примыкает слева). Сравнение метрик
ведётся именно с ним (например, неделя Пн–Вс сравнивается с прошлой Пн–Вс).

## Дальнейшее развитие

- Bitrix REST API как альтернативный `ingestion`-вход (этап MVP-2).
- Bitrix API должен автоматизировать числитель конверсии; Метрика и AppMetrica
  уже дополняют витрину сохранённым верхом воронки.
